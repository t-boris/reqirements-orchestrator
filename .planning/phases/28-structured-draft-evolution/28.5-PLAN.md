# Phase 28 Plan 05: User Input Classification

**Objective:** Classify user inputs as choice/opinion/question and prevent question repetition after direct answers (R3, R7, R10).

**Mantra:** If user input represents a decision, bot must act, not discuss.

---

## Requirements Mapping

| Requirement | Description | Implementation |
|-------------|-------------|----------------|
| R3 | Bot transitions from questions to action | After answer detected, apply -> show -> continue |
| R7 | Distinguish choice vs opinion vs question | InputClass enum + LLM classification |
| R10 | No question repetition after direct answer | AnsweredQuestionsStore persistence |

## DoD Tests

- **T3:** User answers "Only epics" → Bot does NOT ask "Would you like epics or full plan?" again → Draft.scope = EPICS_ONLY is locked.

---

## Analysis

### Current State

1. **answer_matcher.py** classifies user responses to pending questions (matches answers with confidence scores)
2. **extraction.py** processes matches and clears `pending_questions` when all answered
3. **decision.py** has `MAX_REASK_COUNT = 2` but no cross-session persistence
4. **No distinction** between:
   - **Choice** ("Split into epics") → immediate ACTION required
   - **Opinion** ("I think we should...") → continue DISCUSSION
   - **Question** ("Should we split?") → ANSWER and continue

### What Needs to Change

1. **Input Classification** (R7): Classify user input type to route appropriately
   - CHOICE: Structural decision requiring immediate action
   - OPINION: Preference expression, discussion continues
   - QUESTION: User asking something, needs answer
   - ANSWER: Direct response to bot's question

2. **Question Tracking** (R10): Store answered questions to prevent re-asking
   - Persist answered questions per thread
   - Before asking, check if question was already answered
   - Lock fields that were definitively answered

3. **Action Transition** (R3): When CHOICE detected:
   - Mutate draft immediately
   - Show updated structure
   - Continue to next step (not re-ask)

class InputClass(str, Enum):
    """Classification of user input type."""
    CHOICE = "choice"      # Structural decision -> ACTION
    OPINION = "opinion"    # Preference -> DISCUSSION
    QUESTION = "question"  # User asking -> ANSWER
    ANSWER = "answer"      # Response to bot question
    UNCLEAR = "unclear"    # Cannot determine

class InputClassification(BaseModel):
    input_class: InputClass
    confidence: float
    structural_action: Optional[str]  # For CHOICE: split_to_plan, change_scope, etc.
    answered_field: Optional[str]     # For ANSWER: which field was answered
    reason: str
```

Classification rules:
- CHOICE signals: imperative commands ("split", "merge", "add", "only epics")
- OPINION signals: hedging ("I think", "maybe", "could"), conditionals
- QUESTION signals: interrogative ("should we?", "is it?", "do you think?")
- ANSWER signals: response following pending_questions context

class AnsweredQuestion(BaseModel):
    question_key: str          # Normalized question identifier (e.g., "acceptance_criteria")
    original_question: str     # Full question text that was asked
    answer: str               # User's answer
    answered_at: datetime
    answered_by: str          # user_id

class AnsweredQuestionsStore:
    async def record_answer(
        channel_id: str,
        thread_ts: str,
        question_key: str,
        original_question: str,
        answer: str,
        user_id: str,
    ) -> None

    async def was_answered(
        channel_id: str,
        thread_ts: str,
        question_key: str,
    ) -> bool

    async def get_answered(
        channel_id: str,
        thread_ts: str,
    ) -> list[AnsweredQuestion]

    async def filter_unanswered(
        channel_id: str,
        thread_ts: str,
        questions: list[str],
    ) -> list[str]
```

Question keys are normalized from question text:
- "What are the acceptance criteria?" -> "acceptance_criteria"

## Decisions

- **Question key normalization:** Map question text to field names for consistent tracking
- **Persistence strategy:** Store in answered_questions table (not in-memory state)
- **Confidence threshold:** 0.7 minimum to record an answer as definitive
- **CHOICE detection:** LLM-based with imperative command patterns

| Missing CHOICE classification | Conservative: default to normal flow if unclear |
| DB overhead | Batch queries where possible, non-blocking |
